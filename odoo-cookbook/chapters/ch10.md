## Core Concepts

- **5 security layers**: (1) menu `groups` → (2) model ACLs → (3) field `groups` → (4) record rules → (5) view element `groups`.
- **Groups hierarchy**: `category_id` (application), `implied_ids` (inherited groups). Linearly linked via `implied_ids` = dropdown in user form; otherwise checkboxes.

## Techniques

- **Groups definition**: `<record id="group_user" model="res.groups"><field name="name">User</field><field name="implied_ids" eval="[(4, ref('base.group_user'))]"/></record>`.
- **ACL CSV**: `id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink`.
- **Record rules**: `<record model="ir.rule"><field name="domain_force">[('user_id','=',user.id)]</field></record>` — domain filter per group.
- **Field groups**: `<field name="salary" groups="hr.group_hr_manager"/>` — field invisible to non-members.
- **View element groups**: `groups="module.group_name"` on `<button>`,`<menuitem>`,`<field>`,`<notebook>`,`<group>`.
- **Superuser**: `sudo()` bypasses ACLs and rules. `self.env.su` checks superuser status.
- **Feature activation**: Groups can control which features are available — combine with menu/field visibility.

## Pitfalls

- Admin does NOT auto-receive ACLs — must be explicitly defined in CSV.
- `sudo()` bypasses record rules — risk of data leakage to wrong users/companies.
- Group names in stage filters break in non-English languages (translatable).
