## Core Concepts

- **Kanban stages**: `project.task`-style progression with `stage_id` + `kanban_state`. Stage model requires `fold` (boolean, folds into dropdown in statusbar) and `sequence` (ordering).
- **Automation rules**: Technical → Automation → Automation Rules. Trigger: time-based (date field + delay) or event-based (create/edit/delete on model).

## Techniques

- **Server actions**: Create via Technical → Actions → Server Actions. Types: `python_code`, `email`, `create`, `write`, `multi`.
- **Python code server actions**: Write arbitrary Python with `records`, `record`, `env`, `log()`, `action` context. No debug support.
- **Time-based automation**: Trigger = "Based on date field", pick `date_deadline`, delay `-1 Days`. Domain: `["&",["date_deadline","!=",False],["stage_id.fold","=",False]]`.
- **Event-based automation**: Trigger = "On create and edit" + "When updating field: Stage". Pre-update domain + post-update domain detects transitions.
- **QWeb PDF reports**: `<t t-call="web.html_container"><t t-foreach="docs" t-as="doc">` — HTML → Wkhtmltopdf. Register via `ir.actions.report`.
- **Activities**: `mail.activity` model with `activity_type_id`, `date_deadline`, `user_id`, `summary`. Manageable from Kanban cards.
- **Stat buttons**: `<button type="object" name="action_view_rooms" class="oe_stat_button" icon="fa-bed"/>` — show counts on form header.
- **Archive**: `<field name="active" invisible="1"/>` enables archive/unarchive via the action menu.

## Pitfalls

- Python code in server actions cannot be breakpoint-debugged — log-debug only.
- Automation rules' "Check Action Rules" cron runs every 4h by default — time-based rules fire at most once.
- Stage name filters break on translated interfaces.
